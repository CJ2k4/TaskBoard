# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

TaskBoard is a real-time collaborative Kanban board (shared boards → columns → cards, drag-and-drop, live multi-user sync). The project is in early build-out: **read `project-scope.md` (the "what", including the full data model) and `implementation-plan.md` (the ordered "how") first** — they are the source of truth for the schema, milestone sequencing, and the design decisions summarized below. When implementing, follow the milestone order in `implementation-plan.md` (M0 scaffolding → M1 auth → M2 CRUD → M3 drag-and-drop → M4 roles → M5 real-time).

## Current state

**M0–M5 are done front to back — the project's entire planned scope (`implementation-plan.md`) is complete.** TaskBoard is a working real-time collaborative Kanban board. Any further work is the M6 stretch list or polish.

- `server/` — Spring Boot backend. Postgres wired via `docker-compose.yml`, Flyway migrations `V1__baseline` (empty) + `V2__app_user` + `V3__board_graph` (board, board_membership, board_column, card). Auth is complete (register/login/refresh JWTs, JWT filter, `GET /api/me`). **M2 board CRUD is complete**: `/api/boards` (POST/GET/GET{id}/PATCH/DELETE, where `GET /{id}` returns the whole board nested), `/api/boards/{id}/columns` + `/api/columns/{id}` (PATCH/DELETE, delete blocked if non-empty), `/api/columns/{id}/cards` + `/api/cards/{id}`. **M3 move endpoints are complete**: `PATCH /api/cards/{id}/move` (`{targetColumnId, beforeCardId?, afterCardId?}` — after wins if both; neither = append; anchors resolved against server order; target column must be on the card's board) and `PATCH /api/columns/{id}/move` (`{beforeColumnId?, afterColumnId?}`); responses carry the resolved rank to reconcile to. Ordering uses `common/ranking/LexoRank` (server-authoritative; `between` for placement, `spread` for the rank-exhaustion re-balance — services catch `RankExhaustedException`, re-space via `rebalanceRank` (which deliberately does **not** bump `updatedAt`), and retry once). **M4 backend (sharing + roles) is complete**: `POST /api/boards/{id}/invites` and `GET /api/boards/{id}/members` (nested under the board), `PATCH`/`DELETE /api/memberships/{id}` (by row id); an invite to an unregistered email is `PENDING` and is activated by `PendingInviteResolver`, which listens for `UserSignedInEvent` (published by `AuthService` on register **and** login) via `@TransactionalEventListener(AFTER_COMMIT)` + `@Transactional(REQUIRES_NEW)` — auth never imports board, so the dependency arrow stays one-way. Access is now **membership-scoped**: the single guard `BoardService.requireBoardAccess(boardId, userId, Role)` (with `Role.atLeast` as the OWNER>EDITOR>VIEWER ladder) returns **404** when the caller has no ACTIVE membership (hides existence) and **403** when they're a member whose role is too weak; ownership is proven by the `OWNER` `board_membership` row, not `board.owner_id`. Required levels: VIEWER to read a board or its members, EDITOR for every column/card mutation, OWNER for board rename/delete and all member management. `GET /api/boards` returns boards where the user is any active member (`BoardService.listAccessible`), and both `BoardResponse` and `BoardDetailResponse` carry **`myRole`** so the client can render read-only without probing for 403s. **M5 backend (real-time) is complete**: a STOMP-over-WebSocket endpoint at **`/ws`** with Spring's simple broker on `/topic`, all under `realtime/` (`config/WebSocketConfig`, `security/StompAuthChannelInterceptor`, `service/BoardEventBroadcaster`, `dto/BoardEvent`). The handshake is `permitAll()` in `SecurityConfig` **by necessity** (a browser can't set an `Authorization` header on a WebSocket upgrade); identity is proved one frame later on **STOMP CONNECT** via an `Authorization: Bearer <accessToken>` native header, and **SUBSCRIBE** to `/topic/board/{id}` is authorized by the same `requireBoardAccess(…, Role.VIEWER)` guard — anything else throws `StompSecurityException`, which closes the session (refusal is terminal; there is no "401 later" on a stream). Services stay ignorant of WebSockets: every mutation publishes a `board/service/BoardChangedEvent`, which `BoardEventBroadcaster` relays with `@TransactionalEventListener(AFTER_COMMIT)` — so the arrow is `realtime → board` only, and nothing is announced that can still roll back (note the corollary: an event published outside a transaction is *silently dropped*). Wire shape is `{type, boardId, actorId, at, payload}` where `type` is `board/dto/BoardEventType` and fixes the payload: `CARD_*`→`CardResponse`, `COLUMN_*`→`ColumnResponse`, `BOARD_UPDATED`→`BoardSummary` (**not** `BoardResponse` — `myRole` is per-caller and must not be broadcast), `MEMBER_*`→`MembershipResponse` (removal included, so the removed user recognizes themselves by `userId`), and all `*_DELETED`→`DeletedRef`. `actorId` exists so an optimistic client can skip its own echo. Rank re-balances are deliberately **not** broadcast (re-spacing preserves relative order, and clients never compute placements locally). Also `GET /api/health` (M0), a global exception handler (404/403/409/401/400/500 → `ApiError`), and CORS for the Next.js origin. **105 tests** (`RealtimeIntegrationTest` drives a real STOMP client over a real port); `board/` and `realtime/` mirror the `auth/` feature-first/layered layout.
- `frontend/` — Next.js 16 App Router app (`src/app`, `src/lib`, `src/components`). Auth UI complete (register/login, `AuthProvider`, `<Protected>` guard). **M2 board UI complete**: the dashboard (`/dashboard`) is the board list (create/rename/delete), and `/boards/[id]` renders columns + cards with create/rename/delete and a portal card modal for editing. Board data goes through `src/lib/boards.ts`; all authenticated calls use `useAuth().authFetch`, which attaches the access token and transparently refreshes-on-401 + retries once. Destructive actions use an inline two-step confirm (`InlineConfirmButton`), never `window.confirm`. **M3 card drag-and-drop is done** (`@dnd-kit`): `/boards/[id]` wraps columns in a `DndContext`; cards are `useSortable` (via `components/board/sortable-card.tsx`), each column's card area is a droppable, and a pointer-sensor activation distance (~8px) keeps cards click-to-open *and* draggable. On drop the board updates optimistically then reconciles to the server's returned rank via `moveCard` (intent: `{targetColumnId, beforeCardId?, afterCardId?}`); a drag-start snapshot rolls back on failure. **Column dragging is also done**: columns are `useSortable` with a grip handle in the header (the only drag source, so the click-to-rename title / delete / add-card stay interactive), in a horizontal `SortableContext`; one `DndContext` holds both cards and columns, disambiguated by a custom `collisionDetection` that filters candidates by `active.data.current.type` (card-drop targets are namespaced `cards:{columnId}` to avoid id collision with the column sortable). **M4 sharing UI is done**: `src/lib/members.ts` wraps the membership endpoints and `components/board/share-modal.tsx` is a portal modal (Share button in the board header) with the invite form (email + EDITOR/VIEWER — never OWNER), the roster (PENDING rows badged and labelled "Hasn't signed up yet"), per-row re-role and remove — all owner-only, while any member may read the list. **Permissions are derived once** in `/boards/[id]` from the server's `myRole` (`canEdit = myRole !== "VIEWER"`, `isOwner = myRole === "OWNER"`, both null-guarded) and passed down as booleans — components take booleans, never the role, so policy lives in one place. Controls a role can't use are **not rendered** (not merely disabled, and never render-then-403): viewers get no composers, no delete buttons, no grip handles, a plain title, a read-only card modal, and `useSortable({ disabled: true })`; the drag handlers also early-return on `!canEdit` as defence in depth. The dashboard lists shared boards too, badged with the caller's role and without rename/delete unless they own it. **M5 real-time UI is done** (`@stomp/stompjs`): `src/lib/realtime.ts`'s `useBoardEvents` hook opens one STOMP connection per open board — auth rides the **CONNECT frame** (`beforeConnect` reads the access token fresh each (re)connect, so a mid-session refresh is picked up; the client never SENDs), subscribes to `/topic/board/{id}`, and on a *re*-connect calls the page's `load()` (the simple broker has no replay). `onEvent`/`onResync` are held in refs (deps are only `boardId`/`enabled`) so the socket isn't rebuilt on every keystroke. `src/lib/board-events.ts`'s **pure** `applyBoardEvent(board, event)` folds `CARD_*`/`COLUMN_*`/`BOARD_UPDATED` into `BoardDetail` (create/update/move share one path; everything re-sorts by server `rank`, never arrival order); `BOARD_DELETED` and `MEMBER_*` are identity-/navigation-dependent so the board page's `handleBoardEvent` owns them. The page **skips its own echo** (`actorId === user.id`), shows a Live/Reconnecting dot, patches `board.myRole` on a live `MEMBER_UPDATED`-about-me (so `canEdit` flips with no reload), shows a calm terminal note (not a redirect) on `BOARD_DELETED` / self-`MEMBER_REMOVED`, and bumps a nonce passed to `ShareModal` so an open roster refetches on any `MEMBER_*`. The card modal warns ("someone else changed/deleted this") instead of clobbering an open draft — last-write-wins made visible. Landing page (`/`) still shows the backend health status.
- Tokens are returned **in the response body** (access + refresh), not httpOnly cookies. Frontend keeps the **access token in memory** and the **refresh token in `localStorage`**, bootstrapping the session from it on load; the browser calls the backend directly, so client-side auth calls use `NEXT_PUBLIC_API_URL` (the health check still uses the server-only `API_BASE_URL`). Google OAuth is deliberately deferred (`app_user.password_hash` is nullable to leave room for it).

## Backend commands (run from `server/`)

Requires a **JDK 21** on `JAVA_HOME` (`pom.xml` pins `java.version=21`); the build fails on older JDKs. Uses the Maven wrapper — always `./mvnw`, not a system `mvn`.

```bash
./mvnw spring-boot:run                       # run the app locally
./mvnw clean package                         # compile + test + build jar
./mvnw test                                  # run all tests
./mvnw test -Dtest=ClassName                 # single test class
./mvnw test -Dtest=ClassName#methodName      # single test method
./mvnw clean package -DskipTests             # build without tests
```

**Postgres must be running** (`docker compose up -d` from the repo root) or the Spring context won't start — `spring-boot:run`, `contextLoads`, and `AuthIntegrationTest` all need a live datasource. `AuthIntegrationTest` boots the whole app and drives every auth endpoint, so a green `./mvnw test` is a strong signal the wiring is intact; it's the safety net to lean on when refactoring.

## Stack specifics that will bite if unknown

- **Spring Boot 3.5.16 on Java 21.** Standard Boot 3 starters (`spring-boot-starter-web`, `-data-jpa`, `-security`, `-validation`, `-websocket`), with `spring-boot-starter-test` + `spring-security-test` for tests. Flyway is `flyway-core` + `flyway-database-postgresql`; Postgres driver is `runtime` scope.
- **Base package is `org.cj.server`** (groupId `org.cj`). New code goes under here. The plan's package split (`auth/`, `board/`, `membership/`, `realtime/`, `common/`) lives under `org.cj.server`.
- **Package layout is feature-first, then layered inside each feature.** Follow the shape `auth/` already sets — `board/` and `membership/` must mirror it rather than inventing their own:

  ```
  org.cj.server.auth
  ├── entity/       User                     (JPA entities)
  ├── repository/   UserRepository           (Spring Data)
  ├── dto/          RegisterRequest, AuthResponse, TokenPair, …
  ├── service/      AuthService, JwtService  (business logic, HTTP-agnostic)
  ├── controller/   AuthController, MeController
  └── security/     SecurityConfig, JwtAuthenticationFilter, AuthPrincipal
  ```

  `common/` follows the same idea (`exception/`, `dto/`, `controller/`). Everything stays under `org.cj.server`, so `@SpringBootApplication` component-scans it all with no extra config.

  **Dependency direction:** `controller → service → repository → entity`, with `dto` as the shared vocabulary. **A `dto` must never import a `service`** — that's why the token pair is `dto/TokenPair` rather than a record nested in `JwtService`. Mapping DTO↔entity via a static factory on the DTO (`UserResponse.from(user)`) is the accepted pattern here; don't add a `mapper/` layer at this scale.
- **Database migrations are Flyway** — schema changes go in `src/main/resources/db/migration/` as versioned SQL, never via `ddl-auto`.

## Architecture decisions to respect (from the scope docs)

These are already decided — implement to them rather than re-deriving. The full column-level schema (types, PKs, FKs, constraints, indexes) lives in `project-scope.md` under `## Data`.

- **Ordering / drag-and-drop uses fractional rank strings** (LexoRank-style), stored as a `rank varchar` on Column and Card. Moves are expressed as *intent* (`move card before/after X`); the **server computes the canonical rank and is authoritative** — clients reconcile to the server's result. This holds even in the single-user path so nothing changes when real-time arrives. The ranking utility (`rankBetween`) is the highest-risk unit — unit-test it exhaustively.
- **Access control is per-board membership** (`board_membership` with roles `OWNER`/`EDITOR`/`VIEWER`, status `ACTIVE`/`PENDING`). Enforce roles server-side from the start (Spring Security `@PreAuthorize` / service guards), not later. Viewers are read-only.
- **Auth is JWT (stateless)** via Spring Security — access + refresh tokens, since the Next.js frontend is a separate origin.
- **Real-time is native Spring WebSocket + STOMP** (`/topic/board/{id}`), no external pub/sub. Publish change events **after DB commit**. Conflict policy: server-authoritative ordering + last-write-wins on field edits keyed by `updated_at`. Build roles (M4) before real-time (M5).
- **Reserved-word table names:** `User` → table `app_user`, `Column` → table `board_column`. Use these mappings on the JPA entities.
- **Enums stored as strings** (`@Enumerated(EnumType.STRING)` + a DB `CHECK` constraint), never ordinals.
- **UUID primary keys, app-generated** (not DB serials). Timestamps are `timestamptz` / `Instant`, UTC.
- **`card.board_id` is denormalized** (a card also references its board directly, not only via its column) for board-scoped auth checks and whole-board loads — keep it in sync on cross-column moves.
- Scale target is small (≤10 concurrent users per board); do not over-engineer the real-time layer.
